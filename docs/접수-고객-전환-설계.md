# 접수를 고객으로 만드는 과정 — 설계 (2026-09-05)

상태. **설계 확정, 구현 전.** 대표 지시 "마케팅으로 온 손님을 고객으로 만드는 과정을 짜줘".
지금은 홈페이지 점검 위젯과 우리결혼중개 사이트에서 들어온 접수가 마케팅 센터 목록에 쌓이기만 하고,
그다음이 없다. 장보고(시범)이 고객 관리에 안 보였던 것이 그 증거다. 접수와 고객 사이의 길을 놓는다.

## 1. 한 줄 요약

**접수(연락처만 남긴 손님) → 첫 연락 → 상담 → 고객 등록 → 계약.** 접수함이 이 다섯 칸을 따라 손님을
옮기고, 대표는 버튼 하나로 다음 칸으로 보낸다. 고객으로 등록되는 순간 점검 결과와 상담 기록이 고객
문서에 따라가서 같은 질문을 두 번 하지 않는다.

## 2. 손님 쪽에서 본 흐름

| 단계 | 손님이 한 일 | 대표가 할 일 | 화면에서 누르는 것 |
|---|---|---|---|
| ① 접수 | 점검 결과를 보고 성함·연락처를 남김. 대개 밤이다 | 문자로 알림 받음 | (자동) |
| ② 첫 연락 | 전화를 받음 | **당일, 늦어도 다음날 오전에** 전화. 점검 결과를 먼저 읽어 준다 | 「전화했음」 |
| ③ 상담 | 궁금한 것을 물음. 가족 눈치, 비용, 나라 | 비용표·환불 조건·나라별 규정을 사실대로. 다시 연락할 날을 정한다 | 「상담 중」 + 다음 연락일 |
| ④ 고객 등록 | 진행 의사를 밝힘 | 고객으로 등록. 서류 목록과 42개 의무 타임라인이 자동으로 열린다 | 「고객으로 등록」 |
| ⑤ 계약 | 계약서 서명 | 기존 고객 관리 흐름 | (고객 관리) |
| 종료 | 연락이 끊기거나 조건이 안 됨 | 사유를 남기고 닫는다. 명절 앞에 다시 볼 명단이 된다 | 「종료」 + 사유 |

손님 심리 리서치가 정한 규칙이 여기 붙는다. 첫 전화는 재촉이 아니라 확인이다("점검 결과 보니
소득 쪽만 서류로 확인하면 되겠더라고요"). 판단하지 않는 말투, 비용 전부 공개, 상대 분을 사람으로 부르기.

## 3. 데이터

### 3-1. 접수 문서 `agencies/{aid}/leads/{leadId}` — 지금 있는 것에 더한다

| 필드 | 값 | 비고 |
|---|---|---|
| `status` | `new` → `contacted` → `consulting` → `converted` / `closed` | 지금은 `new`만 쓴다 |
| `contactedAt` | 첫 연락 시각 | 「전화했음」 누를 때 |
| `nextActionAt` | 다시 연락할 날 | 「상담 중」 누를 때 고른다. 지나면 대시보드에 뜬다 |
| `memo` | 통화 메모 | 있는 필드. 상담일지 노트를 대신한다 |
| `closedAt`, `closeReason` | 종료 시각·사유 | `no_response`(연락 두절) / `not_eligible`(조건 미달) / `other_agency`(타업체) / `hold`(보류) / `other` |
| `clientId`, `convertedAt` | 등록된 고객 id·시각 | 「고객으로 등록」 성공 시 |

`source`(`quick_check` / `woori_site`)와 `summary`(점검 결과)는 그대로 쓴다.

### 3-2. 고객 문서 `agencies/{aid}/clients/{clientId}` — 선택 필드 하나

```
source?: { type: 'lead' | 'manual' | 'referral'; leadId?: string; via?: string }
```

기존 고객은 필드가 없으면 `manual`로 본다. 이관 작업 없음.

### 3-3. 등록 때 고객으로 넘어가는 것

| 접수 | 고객 |
|---|---|
| `name` | `koreanClient.name` |
| `phone` | `koreanClient.phone` |
| 점검 요약의 혼인 상태(미혼·이혼 확정·사별) | `koreanClient.maritalHistory` (none·divorced·widowed) |
| `summary` 전체 | 고객 첫 상담 메모로 저장 |
| 접수 id | `source.leadId` |

생년월일·주소·직업·연소득은 접수에 없다. 등록 창에서 대표가 채운다. 점검 요약의 "연 약 2,520만~4,200만 원"
같은 구간은 숫자로 옮기지 않는다. 틀린 숫자가 문서에 박히는 것보다 빈칸이 낫다.

### 3-4. 보안 규칙

`agencies/{aid}/leads`의 업체 수정 허용 필드를 `status, memo, updatedAt`에서
`status, memo, updatedAt, contactedAt, nextActionAt, closedAt, closeReason, clientId, convertedAt`로 넓힌다.
이름·전화·요약·출처는 여전히 화면에서 못 바꾼다. 고객 문서에 `source`를 넣는 것은 기존 생성 규칙으로 된다.

## 4. 화면

### 4-1. 접수 목록은 마케팅 센터에서 「고객 관리」로 옮긴다

지금은 마케팅 센터 카드 안에 있다. 마케팅 센터는 상품을 사는 곳이고, 접수 처리는 매일 하는 일이다.
「고객 관리」 화면 위에 **탭 두 개**를 둔다. 「접수」와 「고객」. 접수 탭이 이 설계의 본체다.

접수 한 줄에 보이는 것.
- 이름 · 전화(누르면 바로 전화) · 판정 배지(걸림 없음/확인 필요/정리 필요) · 어디서 왔나(위젯/홈페이지)
- 접수 시각과 **경과 시간**("어젯밤 11:20 · 11시간 전"). 미연락 24시간이 넘으면 붉게.
- 상태와 다음 연락일
- 버튼. 「전화했음」 「상담 중」 「고객으로 등록」 「종료」. 상태에 따라 다음 버튼만 진하게.
- 펼치면 점검 결과 전문과 메모 입력란

마케팅 센터에는 「이번 달 접수 N · 연락 M · 고객 등록 K · 전환율」 한 줄과 접수 탭으로 가는 링크만 남긴다.
마케팅 돈을 낸 사람이 성과를 보는 자리는 거기가 맞다.

### 4-2. 「고객으로 등록」

기존 「신규 고객 등록」 창(`CreateClientDialog`)을 그대로 열되 이름·연락처·혼인이력을 채워서 연다.
창 위에 "점검 접수에서 온 손님입니다. 점검 결과가 고객 메모에 함께 저장됩니다" 한 줄.
등록이 끝나면 접수는 `converted`가 되고 고객 상세로 이동한다. 고객 상세 머리에
"홈페이지 점검 접수 · 확인 필요 2건"처럼 출처와 판정이 보인다.

### 4-3. 대시보드

상단 카드 넷 중 「진행 중 고객」 옆에 **「새 접수」** 카드. 숫자는 `new` 건수, 힌트는 "24시간 넘게 연락 안 한 N건".
누르면 접수 탭. 「조치 필요 항목」 목록 맨 위에 미연락 접수와 다음 연락일이 지난 접수가 올라온다.
법정의무 항목과 같은 줄에 두는 이유는 하나다. 대표가 아침에 보는 목록이 하나여야 한다.

### 4-4. 문자

- 접수 문자는 지금처럼 즉시 1통(있음).
- **아침 9시 요약 문자**(선택). "새 접수 2건, 다시 연락할 손님 1명" 한 줄과 접수 탭 링크. 밤에 온 접수를
  아침에 처리하는 습관을 만든다. 기존 기한 알림 함수(`checkExpiringDocuments`)와 같은 예약 방식.

## 5. 재는 것

마케팅 센터에 월별 표 하나.

| 달 | 접수 | 첫 연락(24시간 내) | 상담 | 고객 등록 | 전환율 | 출처별 |
|---|---|---|---|---|---|---|

전환율은 `converted / 접수`. 출처별로 갈라 보면 홈페이지 위젯과 우리결혼중개 사이트 중 어느 쪽이 손님을
데려오는지 보인다. 이것이 블로그·AEO 상품의 "결과로 증명"이 된다. 누나 인터뷰의 월 30명 접촉·1팀 성사(3.3%)가
기준선이다.

## 6. 구현 순서와 크기

| 순서 | 일 | 크기 |
|---|---|---|
| 1 | 규칙 필드 확장 + 접수 타입 확장 + 접수 탭(목록·상태 버튼·메모) | 1일 |
| 2 | 「고객으로 등록」 프리필 + `converted` 기록 + 고객 `source` + 첫 메모 | 반나절 |
| 3 | 대시보드 「새 접수」 카드 + 미연락·다음 연락일 경고 | 반나절 |
| 4 | 마케팅 센터 월별 전환 표 | 반나절 |
| 5 | 아침 요약 문자 (선택) | 반나절 |
| 6 | 검증 — 장보고(시범)을 고객으로 등록해 보고 지운다, 규칙 거부 경로, 모바일 화면 | 반나절 |

체크리스트는 착수할 때 `docs/checklist-leads.md`로 만든다.

## 7. 열린 질문

- 접수 탭을 「고객 관리」에 둘지, 사이드바에 「상담 접수」 메뉴를 따로 둘지. 이 설계는 탭을 권한다.
  메뉴가 늘면 대표가 안 본다.
- 종료 사유 목록이 충분한지. 현장에서 자주 나오는 사유를 대표에게 한 번 물을 것.
- 아침 요약 문자를 기본으로 켤지. 문자 한 통에 20원 안팎이라 비용은 문제가 아니고, 귀찮음이 문제다.
- 우리결혼중개 사이트의 이어진 대화(`--- 이어진 대화 ---`)가 접수 요약에 계속 덧붙는데, 고객으로 등록한 뒤에
  덧붙는 대화도 고객 메모로 따라가게 할지.
