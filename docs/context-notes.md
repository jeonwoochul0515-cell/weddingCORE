## 2026-09-06 · 네이버 검색광고를 처음 여는 일

설계와 실측은 `docs/광고체계-2026-09-06.md`. 여기에는 다음 사람이 걸릴 함정만 남긴다.

### 비즈채널을 API로 만들 수 있다 (전역 CLAUDE.md의 "수동 등록" 설명은 낡았다)
`POST /ncc/channels`가 된다. 다만 두 가지를 맞춰야 한다.
- **`channelKey`만 보내면 `1002 URL 형식에 맞지 않습니다`** 가 난다. URL을 어떻게 바꿔도 같다.
  `businessInfo: {site, siteName}` 을 함께 보내야 통과한다. 오해하기 딱 좋은 에러 문구다.
- **사이트 이름은 10자 이내.** "weddingCORE"(11자)가 거절돼 "웨딩코어"로 만들었다.
  광고에 그대로 노출되는 이름이라 어차피 우리말이 낫다.

만든 뒤에는 `status: PAUSED` / `BUSINESS_CHANNEL_UNDER_REVIEW`로 심사에 들어간다.

### 광고를 살 자리는 검색량이 아니라 값으로 고른다
결혼정보회사(7,500회)는 3위 73,200원이고, 결혼중개업자본금(20회)은 70원이다.
**둘의 차이는 경쟁이 아니라 의도다.** 앞의 말을 치는 사람은 짝을 찾는 소비자이고
뒤의 말을 치는 사람은 업소 사장이다. 우리 손님은 뒤쪽이다.

거의 모든 중간 가격대 키워드가 **5위로 내리면 70원**이 된다(결혼중개업법 1,660 → 70).
3위만 재고 "비싸다"고 접으면 살 수 있는 자리를 놓친다. **두 순위를 같이 재라.**

### 캠페인은 여전히 API로 못 만든다
`POST /ncc/campaigns` → `1018`. 전역 CLAUDE.md §13의 2026-07-20 결론대로 **재시도하지 않았다.**
화면에서 1개 만들고 그 id를 받아 `scripts/naver-ads-setup.py --apply`를 돌린다.

- 「막힘」 등급 전부와 이번에 고친 것만 체크리스트에 옮겼다. 「위험」은 다음 세션이 먼저 볼 것 12건만 요약.

- 15번(문구·용어 전수) 보고서는 없다. 중단 전에 끝나지 않은 것으로 보인다. 영어 소제목은 직접 전수 조사해 고쳤다.

### 이번에 내린 결정
- **기한 지남 필터는 훅 하나를 대시보드와 목록이 같이 쓴다**(`useOverdueClients`). 두 화면이 각자 세면 숫자가 어긋난다.
- **「법적 위반」이라는 이름을 버렸다.** `warning`/`violated`는 기한을 3일 이내로 넘겼느냐 넘게 넘겼느냐의 구분이지
  법적 판단이 아니다. 「기한 지남 · 3일 이내 / 3일 넘김」으로 부른다.
- **시스템이 알 수 없는 값은 점수로 보여 주지 않는다.** 마케팅 「검색 준비도 40점」은 모든 업체에 같은 상수였다.
  이번 달 접수 실적(진짜 값)으로 바꾸고, 준비 체크는 완료 표시 없는 안내 목록으로.
- **휴대폰 층 순서.** 창·서랍 `z-[60]` > 하람 위젯 `z-50` > 하단 메뉴 `z-40` > 더보기 배경 `z-30`.
  하람 위젯은 업무 화면(`/agency|/lawyer|/admin`)에서만 `bottom-[4.25rem]`로 올린다.
- **AI 초안 경고는 항목마다가 아니라 목록 아래 한 줄.** 42번 겁 줄 필요가 없다. 사무소명은 전역 §18대로
  「법률사무소 청송law(담당변호사 김창희)」.
- **동의 증빙에 양식은 없다고 화면에 밝힌다.** 계약서 조항·서명·문자 답장 모두 된다. 「문서번호」를 요구하지 않는다.
- **시뮬레이터 결과의 「변호사 상담」은 손님 화면이므로 업체 로그인이 아니라 사무소 전화(1660-4452)로 간다.**
- 「고객으로 등록」은 접수 상태(`new`)에서도 보인다. 사무실로 바로 와서 계약하는 손님이 흔하다.

### 업체 정보 고치기 (대표 지시 "업체 정보 고치기부터 이어서")
- **등록 번호(사업자·결혼중개업)는 화면에서 바꾸지 않는다.** 가입 승인의 근거라 관리자가 새 등록증을 보고 바꿔야 한다.
  규칙은 대표가 바꿀 수 있게 열려 있지만 화면은 읽기만 하고, 바꾸는 길(사무소 전화 1660-4452)을 적었다.
- **업체 문서의 `phone`은 곧 접수 문자를 받는 번호다.** `submitCheckLead`가 `agency.phone`으로 문자를 보낸다.
  손님에게 보이는 번호가 아니므로 필드를 둘로 나누지 않고, 기본 정보 화면과 가입 화면 모두 **휴대폰 번호만** 받는다.
  유선번호를 받으면 문자가 조용히 사라진다(점검 11-11).
- 「기본 정보」 탭은 컬렉션이 아니라 업체 문서 자체다. 훅은 조건부로 못 부르므로 `collectionKey`로 자리를 채운다.
- 다섯 탭의 고치기는 추가 폼을 그대로 쓴다(`editingId`). 날짜는 Timestamp → `yyyy-MM-dd`로 되돌려 넣는다.
- **선택 칸은 「선택」 빈 값에서 시작한다.** 첫 값(예: 「허용 확인」)으로 몰래 채워져 "확인 안 했는데 확인한 것"으로
  저장되던 함정(12-4). 기존 기록을 고칠 때도 비어 있으면 골라야 저장된다. 의도한 동작이다.
- 대표 판별은 화면 역할 `agency_owner`와 규칙 역할 `owner`가 이름이 달라 둘 다 대표로 본다.
- 직원 추가·권한(12-3)은 초대 흐름이 따로 필요해 넣지 않았다.

### 배포한 것이 화면에 안 나오면 — 서비스 워커 캐시 (2026-09-06 실측)

배포가 성공(EXIT 0, 새 번들 200)했는데도 브라우저 화면은 **옛 문구 그대로**였다.
이 앱은 `vite-plugin-pwa`의 generateSW로 자산을 precache한다. 그래서 일반 새로고침으로는
옛 번들이 서비스 워커 캐시에서 그대로 나온다. **Ctrl+Shift+R(강제 새로고침)** 을 해야 바뀐다.

- 판별법. `curl`로 새 번들 파일(`dist/assets/…`의 새 해시 이름)이 200이면 배포는 된 것이다.
  화면만 옛것이면 캐시 문제다. 코드나 배포를 다시 의심하지 말 것.
- 대표님이나 업체 화면도 같다. 급한 수정을 배포했으면 강제 새로고침을 안내해야 한다.

### 규칙에서 확인한 것
- `clients` 문서는 업체 구성원이 `agencyId`·`automationConsents`만 빼고 고칠 수 있다. 기본정보 수정과 상태 변경은
  규칙 수정 없이 화면만 만들면 된다.
- 서류 삭제는 Firestore는 되지만 **Storage 규칙에 delete가 없다.** `allow write`에 `request.resource.size` 조건이
  있어 삭제 요청은 평가 자체가 실패한다. `allow delete`를 따로 넣어야 한다.
- 알림 `readBy`는 `write: false`라 화면에서 읽음 처리를 못 한다. `readBy`만 바꾸는 update를 규칙에서 열어 준다.
- 캐럿 계좌이체 신청은 규칙의 packId 목록(`pack_50/200/500`)과 화면(`pack_110/330/550`)이 달라 **항상 거부**된다.
  화면 값이 실제 가격표이므로 규칙을 화면에 맞춘다.

## 2026-09-05 · 접수 → 고객 흐름과 "보고서 형식"

대표 지시 둘. "접수 요약을 원문 덩어리로 보여주지 마라, 학점나비 보고서 방식으로" /
"마케팅센터에서 고객관리로 넘어가는 업무 플로우를 만들어". 설계는 `docs/접수-고객-전환-설계.md`.

### 결정
- **접수 처리는 고객 관리의 「접수」 탭.** 마케팅 센터는 상품을 사고 성과를 보는 곳이라 접수 목록을 빼고
  이번 달 접수·연락·등록·전환율만 남겼다. 매일 하는 일은 매일 보는 화면에 있어야 한다.
- **접수 요약은 파서와 화면을 나눴다.** `parseLeadSummary.ts`가 하나 실장 요약(업체 사이트)과 빠른 점검
  요약(위젯)을 같은 구조로 읽고, `LeadReport.tsx`가 보고서로 그린다. 원문 형식이 바뀌어도 화면은 안 바뀐다.
- **미확인은 값이 아니라 상태.** 표에서 빼고 "아직 못 물은 항목 N개"로 센다. 값 전체가 미확인일 때만
  미확인이고 "동거 여부 미확인"처럼 섞인 것은 확인된 것으로 본다(장보고 실데이터로 검증).
- **판정값이 없으면 판단 문장에서 추론한다.** 우리결혼중개 접수는 `level`이 `unknown`으로 오는데
  "[하나 판단] 대화상 특이 걸림 없음"이 있다. `inferLevel`이 이를 걸림 없음으로 읽는다. 배지·머리 문장이 같은 값을 쓴다.
- **고객 문서에 `source`·`intake`.** 접수에서 온 고객은 점검 결과가 접수 기록으로 따라가 고객 상세 머리에
  보고서로 접혀 있다. 생년월일·주소·직업·연소득은 접수에 없으므로 대표가 채운다. 구간 값을 숫자로 짐작해
  넣지 않는다.
- 접수 수정 규칙은 status·memo·contactedAt·nextActionAt·closedAt·closeReason·clientId·convertedAt만 허용.
  배선영 계정으로 실측 — 상태 변경 통과, 이름 변경 거부.

### 전역 스킬 `보고서형식`

결론과 다음 행동 → 참고와 한계(원문 접힘). 화면·hwpx·문자에 같은 순서.

## 2026-08-29 · 공개 라우트를 늘릴 때 손대야 하는 곳 네 군데

`/guides`를 만들면서 한 군데를 빠뜨려 페이지가 **404 + noindex**로 나갔다. 화면에는
정상으로 보여서 title만 확인하고 넘어갔는데, 상태코드를 보니 404였다. 그 상태로는
검색엔진이 색인하지 않는다 — 검색 유입을 노린 페이지인데 목적이 통째로 무산될 뻔했다.

공개 라우트를 하나 늘리면 **네 곳을 함께 고쳐야 한다.**

1. `src/routes.tsx` — 라우트 등록
2. `scripts/prerender.mjs`의 `ROUTES` — 본문을 정적 HTML로 굽는다
3. `public/sitemap.xml` — 검색엔진에 알린다
4. **`worker/index.js`의 `ROUTE_PREFIXES`** ← 빠뜨린 곳

4번을 빠뜨리면 어떻게 되나. 이 워커는 소프트404를 막으려고 "앱이 처리하는 경로"가
아니면 **내용은 그대로 주되 상태를 404로 바꾸고 robots를 noindex로 바꾼다.** 그래서
브라우저로 열면 멀쩡해 보이고 `grep '<title>'`도 통과한다. `curl -w '%{http_code}'`로
상태코드를 봐야 드러난다.

**배포 검증은 이렇게 한다.**

```bash
curl -s -w "|%{http_code}" https://weddingcore.net/새경로 | tail -c 20   # 200이어야 한다
curl -s https://weddingcore.net/새경로 | grep -c noindex                 # 0이어야 한다
```

## 2026-08-29 · 사고 — 다른 프로젝트 사이트가 weddingcore.net에 배포됐다

**무슨 일이 있었나.** 프리렌더가 KoAdmit 사이트를 렌더해 우리 dist에 덮어썼고, 그대로
배포되어 weddingcore.net에 `KoAdmit — 학생은 한 푼도 내지 않습니다`가 떴다.

**원인.** `scripts/prerender.mjs`가 **포트 4178을 고정**으로 썼다. 로컬 서버를 띄우고
puppeteer로 각 라우트를 렌더하는 방식인데, 같은 머신에서 작업 중이던 KoAdmit이 그 포트를
점유하고 있었다. puppeteer는 그 포트에 붙어 KoAdmit 페이지를 받아왔고, 검증 없이 저장했다.

**놓친 신호.** 빌드 로그의 마지막 줄이 `프리렌더 4개 라우트 완료`에서
**`2개 라우트 완료`로 줄어 있었다.** 나머지는 `Waiting failed: 45000ms exceeded`로 실패했다.
`tail -3`으로 끝부분만 확인하느라 이 변화를 놓쳤고, 오염된 상태로 두 번 더 배포했다.

**고친 것.**
- 포트 고정을 없앴다. `server.listen(0, '127.0.0.1')`로 OS가 빈 포트를 고른다.
  충돌 자체가 생기지 않는다. `server.once('error', reject)`도 붙였다.
- 렌더된 HTML에 `weddingCORE`가 없으면 **저장하지 않고 실패**시킨다. 포트가 겹치지 않아도
  엉뚱한 내용이 들어가는 경로를 막는다.

**앞으로.** 빌드 로그는 마지막 줄만 보지 말고 **`프리렌더 N개 라우트 완료`의 N이 ROUTES
길이와 같은지** 확인한다. 라우트를 늘렸으면 그 수만큼 나와야 한다. 배포 뒤에는
`curl -s https://weddingcore.net | grep '<title>'`로 실제 응답을 한 번 본다.

## 2026-08-29 · 체류만료일 앵커를 넣으며

### 새 필드가 아니라 앵커로 넣은 이유

`Client`에 `stayExpiryDate` 같은 필드를 새로 만들 수도 있었지만 그러지 않았다.
이 프로젝트에는 이미 **앵커 기반 기한 계산**이 있다 — 의무 템플릿이
`dueDateRule: { anchor, offsetDays }`를 갖고, `markAnchorEvent`로 앵커 날짜를 찍으면
`recomputeDueDatesForAnchor`가 그 앵커를 쓰는 항목의 기한을 다시 계산한다.

체류만료일을 앵커(`stay_expiry`)로 넣으면 이 구조에 그대로 얹힌다. 별도 알림 로직도,
별도 계산도 필요 없다. 연장 허가가 나면 새 만료일로 앵커를 갱신하고, 그러면 다음
연장 기한이 자동으로 다시 계산된다.

**다른 앵커와 성격이 하나 다르다.** `entry_date`나 `marriage_registered`는 한 번 찍고
끝나는 시점이지만 `stay_expiry`는 연장할 때마다 갱신되는 값이다. 타입 주석에 적어 두었다.

### 귀화·영주 시점은 계산할 필요가 없었다

혼인신고일(`marriage_registered`) 앵커가 이미 있어서 `offsetDays: 730`이면 끝이다.
F-6는 혼인 상태로 2년 이상 체류하면 영주 변경이나 간이귀화 신청 시점에 이른다.
새 코드를 쓰지 않고 템플릿 한 줄로 해결됐다.

### 의무 세트가 결혼중개업법인데 출입국 항목을 넣은 것

`marriage_brokerage_act` 세트에 출입국관리법·국적법 근거 항목 2개가 들어갔다.
법령 출처는 다르지만 **고객이 우리를 다시 찾는 지점**이라 같은 흐름에 두는 편이
실무에 맞다고 봤다. 나중에 세트를 법령별로 쪼갤 일이 생기면 이 둘을 먼저 옮긴다.

### 백필이 필요 없었던 이유

의무 템플릿은 고객 생성 시점(`onClientCreated`)에 타임라인으로 복사된다. 즉 템플릿을
고쳐도 **기존 고객의 타임라인은 바뀌지 않는다.** 확인해보니 현재 고객이 0명이라
백필이 필요 없었다. 운영 시작 후 템플릿을 고칠 때는 기존 고객에게 항목을 넣어주는
백필 스크립트가 따로 필요하다는 뜻이기도 하다.

## 2026-08-29 · 판례를 화면에 연결하며

### 왜 Firestore 직접 읽기가 아니라 서버 함수인가

이 프로젝트의 다른 공통 데이터(`regulations`, `regulatoryDelta`, `obligationTemplates`)는
`allow read: if isAuthed()` 규칙을 주고 클라이언트가 `onSnapshot`으로 직접 읽는다.
판례도 같은 패턴을 따르는 게 자연스러워 보였지만 그러지 않았다.

이유는 문서 크기다. `precedents`의 `body`는 최대 40,000자, `holding`은 8,000자다.
Firestore 클라이언트 SDK에는 **필드 선택 조회(`select`)가 없어** 문서를 받으면 본문까지
통째로 온다. 목록 20건이면 수백 KB에서 1MB에 이른다. 목록 화면에서 본문은 쓰지 않는데도.

Admin SDK에는 `select()`가 있다. 그래서 서버에서 요약 필드만 골라 내려주고, 본문은
상세를 열 때 단건으로 가져온다. 기존 패턴을 깨는 것이라 이 노트에 이유를 남긴다.

⇒ **다른 공통 데이터를 추가할 때는 기본적으로 rules + 직접 읽기를 쓸 것.** 본문처럼
   큰 필드를 담는 컬렉션일 때만 서버 함수로 우회한다.

### precedents에 보안 규칙을 만들지 않은 이유

클라이언트가 직접 읽지 않으므로 규칙이 필요 없다. 규칙을 열어두면 나중에 누군가
직접 조회를 붙여 위의 크기 문제가 조용히 재발한다. 서버 함수 하나만 창구로 둔다.

### 표현 규칙 — 사례를 결론처럼 보이게 하지 않는다

전역 §21과 로캐디 사고(2026-08-28, 실재가 확인되지 않는 사건번호가 초안에 인용됨)를
같이 적용한다.

- 사건마다 **법제처 원문 링크**를 노출한다. 업체가 실재를 직접 확인할 수 있어야 한다.
- 요건 연결은 낱말 매칭 기반 **자동 분류**다(`requirementConfidence: 'auto'`).
  화면에 그렇게 표시하고, 사람 검수를 거친 것과 구분한다.
- "이런 경우 허가됩니다" 같은 문장을 만들지 않는다. 사건이 어떤 사유로 다투어졌는지까지다.

### 유학 요건 태그는 화면에 내지 않는다

`REQUIREMENT_HINTS`에 `study_*` 키가 남아 있고 태깅도 되어 있지만, 유학 도메인은
2026-08-28 KoAdmit으로 이관했다. weddingCORE 화면에는 F-6·연장 요건만 노출한다.
태그 자체를 지우지 않는 이유는 이미 태깅된 사건이 고아가 되기 때문이다.

### 함수 배포가 "Cannot determine backend specification"으로 실패하면

`firebase deploy --only functions`가 아래 오류로 죽는 경우가 있다.

```
Error: User code failed to load. Cannot determine backend specification. Timeout after 10000.
```

**코드 문제가 아니다.** CLI가 함수 목록을 뽑으려고 코드를 로드하는 데 주는 시간이
10초인데, 이 프로젝트는 함수가 28개라 그 안에 못 끝낸다(로컬 로딩 자체는 0.5초다).

해결 — 탐지 시간을 늘려서 배포한다.

```bash
FUNCTIONS_DISCOVERY_TIMEOUT=120 npx firebase deploy --only functions:이름
```

에러 문구가 "User code failed to load"라 코드를 의심하게 되는데, 먼저
`node -e "import('./lib/index.js')"`로 로컬 로딩을 재보고 정상이면 이 문제다.

### 배포 대상이 두 군데로 나뉘어 있다

- **웹** — Cloudflare Worker `weddingcore` → weddingcore.net / www.weddingcore.net
  (`npm run deploy:cloudflare`. wrangler OAuth는 죽어 있으니 전역 §15-2 토큰을
  `CLOUDFLARE_API_TOKEN`으로 물려야 한다)
- **함수·Firestore·Storage** — Firebase 프로젝트 `sungpan2026`

`firebase.json`에 hosting 설정이 남아 있지만 실서비스 도메인은 Cloudflare가 받는다.
`npm run deploy:all`은 Firebase Hosting으로 올리므로 실제 사이트에는 반영되지 않는다.

**★ `wrangler deploy`를 직접 부르지 말 것.** 사이트는 올라가지만 뒤에 붙은
`npm run indexnow`(검색엔진 통지)와 `npm run score:seo`(점검)가 통째로 빠진다.
겉으로는 "Deployment complete!"라 성공처럼 보여서 알아채기 어렵다.
2026-08-31에 이 방식으로 여러 번 배포해 새 페이지 통지가 나가지 않았다.
반드시 `npm run deploy:cloudflare`를 쓴다(토큰을 환경변수로 물린 상태에서).

같은 기준이 두 저장소에 있으면 한쪽만 갱신되고, 낡은 쪽이 언젠가 화면에 나간다.

최신 수치(대학 명단 2026-02-12, 재정 금액 2025-03-14)까지 지운 것은 **중복 자체가
위험원**이기 때문이다. 명단은 매년 2월, 금액은 요령 개정 때 바뀐다.

`visaRequirements.ts`의 유학 요건 **키는 남겼다.** `REQUIREMENT_HINTS`가 판례 574건을
요건에 연결하는 데 쓰이고 있어, 키를 지우면 태깅된 사건이 어느 요건이었는지 알 수 없게 된다.
분류에 필요한 것은 키와 실마리 낱말이지 수치가 아니다.

### 입학 기준과 비자 기준은 다른 숫자다

## 2026-09-06 · 해외 SaaS 대비 빠진 다섯 가지를 붙이며 알게 된 것

### 팝업이 화면 밖에 뜨면 애니메이션부터 의심한다
`position: fixed`는 조상 중에 이동·확대·회전·흐림 값을 가진 것이 하나라도 있으면
화면이 아니라 그 조상을 기준으로 놓인다. **0만큼 움직인다는 값도 「없음」이 아니다.**
`animation: ... both`로 끝 장면을 붙들어 두면 `translateY(0)`이 계속 남아 있어
그 요소가 기준 상자가 된다. 채움 방식을 `backwards`로 두면 끝난 뒤 원래 값으로 돌아간다.

판별법 — 팝업 요소의 `getBoundingClientRect()`를 재 본다. `inset-0`인데 화면 크기와
다르면 조상 중에 범인이 있다. 조상을 거슬러 올라가며 `transform`·`filter`·`translate`가
`none`이 아닌 것을 찾으면 된다.

### 저장 전에 사진을 올리려면 id를 먼저 만들어야 한다
사진 경로에 대상 id가 들어가므로, 새로 만드는 고객·후보도 등록 창을 열 때 id를 먼저 잡는다
(`newClientId`, `newPartnerId`). 창을 열었다가 그냥 닫으면 올린 사진이 주인 없이 남는데,
지금은 그대로 둔다. 나중에 청소가 필요해지면 하루 지난 주인 없는 사진을 지우는 함수를 둘 것.

### 옛 구성원 문서에는 이메일이 없다
`claimStaffInvite`가 생긴 뒤에 만들어진 구성원만 `email`을 갖는다. 그 전에 만들어진
대표 문서는 없어서 목록에 내부 ID가 그대로 나왔다. 화면에서 나면 내 이메일로 채우고,
남이면 「이메일이 적히지 않은 구성원」으로 적는다.
