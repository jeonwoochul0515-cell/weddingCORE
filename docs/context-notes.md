다음 세션(사람이든 에이전트든)이 같은 판단을 다시 하지 않도록 남긴다.

## 2026-08-29 · 사고 — 다른 프로젝트 사이트가 weddingcore.net에 배포됐다

**무슨 일이 있었나.** 프리렌더가 KoAdmit 사이트를 렌더해 우리 dist에 덮어썼고, 그대로
배포되어 weddingcore.net에 `KoAdmit — 학생은 한 푼도 내지 않습니다`가 떴다.

**원인.** `scripts/prerender.mjs`가 **포트 4178을 고정**으로 썼다. 로컬 서버를 띄우고
puppeteer로 각 라우트를 렌더하는 방식인데, 같은 머신에서 작업 중이던 KoAdmit이 그 포트를
점유하고 있었다. puppeteer는 그 포트에 붙어 KoAdmit 페이지를 받아왔고, 검증 없이 저장했다.

**놓친 신호.** 빌드 로그의 마지막 줄이 `프리렌더 4개 라우트 완료`에서
**`2개 라우트 완료`로 줄어 있었다.** 나머지는 `Waiting failed: 45000ms exceeded`로 실패했다.
`tail -3`으로 끝부분만 확인하느라 이 변화를 놓쳤고, 오염된 상태로 두 번 더 배포했다.

**고친 것.**
- 포트 고정을 없앴다. `server.listen(0, '127.0.0.1')`로 OS가 빈 포트를 고른다.
  충돌 자체가 생기지 않는다. `server.once('error', reject)`도 붙였다.
- 렌더된 HTML에 `weddingCORE`가 없으면 **저장하지 않고 실패**시킨다. 포트가 겹치지 않아도
  엉뚱한 내용이 들어가는 경로를 막는다.

**앞으로.** 빌드 로그는 마지막 줄만 보지 말고 **`프리렌더 N개 라우트 완료`의 N이 ROUTES
길이와 같은지** 확인한다. 라우트를 늘렸으면 그 수만큼 나와야 한다. 배포 뒤에는
`curl -s https://weddingcore.net | grep '<title>'`로 실제 응답을 한 번 본다.

## 2026-08-29 · F-6 사증발급 판례는 더 없다 (재시도 금지)

"판례를 더 모으면 안전한 발급 기준을 만들 수 있지 않나"를 확인하려고 수집 질의를
F-6 쪽으로 다시 던져 봤다. **결과는 신규 0건이다.** 같은 시도를 반복하지 않도록 남긴다.

### 실측 (law-caddy 경유 법제처 조회)

| 질의 | 행정심판 재결례 | 법원 판례 |
|---|---:|---:|
| 사증발급거부처분 | 16건 | 5건 |
| 결혼이민 | 0 | 1 |
| 결혼동거 | 0 | 0 |
| 국민의배우자 | 0 | 0 |
| 배우자초청 | 0 | 0 |
| 결혼사증 | 0 | 1 |
| 재외공관 | 0 | 2(세금 사건) |
| 혼인 | 0 | 160(가사 사건) |

**`사증발급거부처분`으로 나온 21건은 전부 이미 보유 중이다**(문서 ID로 대조 확인).
법령해석례(`expc`)·헌재결정례(`detc`)에서도 사증·결혼이민 관련은 0건이다.

### 왜 없나 — 구조적인 이유다

사증발급 거부는 **외국인이 재외공관에서 받는 처분**이라 우리 법원에 소송할 자격
자체가 오래 다퉈졌다. 우리가 가진 F-6 사증발급 사건 4건 중 **2건이 각하**인 것이
그 흔적이다. 대법원 2017두38874로 원고적격이 열린 뒤에도 사건 수는 적다.

⇒ **판례로 "안전한 발급 기준"을 만들 수 없다.** 자료가 부족한 게 아니라 사건이 없다.
   발급 단계는 공개된 요건(소득·의사소통·주거·초청제한·안내프로그램)을 정확히
   충족시키는 것으로 가고, 판례는 **연장·귀화 단계**에서 쓴다(체류 실태 100건, 귀화 54건).

### 함정 — `혼인`으로 검색하면 안 된다

판례 160건이 나오지만 이혼·재산분할 같은 가사 사건이다. 실제로 우리 데이터의
`f6_authenticity` 37건 중 24건이 1944·1949·1990년대 가사 판례였다
("뇌졸중 혼수상태에서 이뤄진 혼인신고" 같은 것). F-6와 무관하다.

### 그 대신 찾은 것 — 결혼중개업법 법령해석례

`expc` target에 **결혼중개업 관련 유권해석 3건**이 있다. 비자 기준은 아니지만
우리 고객(중개업체)의 의무와 직결된다.

- 여성가족부 — 결혼중개업 금지 국가에서 활동하는 업체와의 **업무제휴 가능 여부**
- 상주시 — 개정 전후 「결혼중개업의 관리에 관한 법률」 적용
- 상주시 — 행정제재처분 권한 변경 시 위반행위 횟수 산정

현재 수집은 `prec`/`decc`만 돈다. `expc`를 넣으려면 `searchList`가 그 target을
지원하도록 손봐야 한다(응답 루트 키가 `Expc`, 배열 키가 `expc`, 항목명은 `안건명`).

## 2026-08-29 · 체류만료일 앵커를 넣으며

### 새 필드가 아니라 앵커로 넣은 이유

`Client`에 `stayExpiryDate` 같은 필드를 새로 만들 수도 있었지만 그러지 않았다.
이 프로젝트에는 이미 **앵커 기반 기한 계산**이 있다 — 의무 템플릿이
`dueDateRule: { anchor, offsetDays }`를 갖고, `markAnchorEvent`로 앵커 날짜를 찍으면
`recomputeDueDatesForAnchor`가 그 앵커를 쓰는 항목의 기한을 다시 계산한다.

체류만료일을 앵커(`stay_expiry`)로 넣으면 이 구조에 그대로 얹힌다. 별도 알림 로직도,
별도 계산도 필요 없다. 연장 허가가 나면 새 만료일로 앵커를 갱신하고, 그러면 다음
연장 기한이 자동으로 다시 계산된다.

**다른 앵커와 성격이 하나 다르다.** `entry_date`나 `marriage_registered`는 한 번 찍고
끝나는 시점이지만 `stay_expiry`는 연장할 때마다 갱신되는 값이다. 타입 주석에 적어 두었다.

### 귀화·영주 시점은 계산할 필요가 없었다

혼인신고일(`marriage_registered`) 앵커가 이미 있어서 `offsetDays: 730`이면 끝이다.
F-6는 혼인 상태로 2년 이상 체류하면 영주 변경이나 간이귀화 신청 시점에 이른다.
새 코드를 쓰지 않고 템플릿 한 줄로 해결됐다.

### 의무 세트가 결혼중개업법인데 출입국 항목을 넣은 것

`marriage_brokerage_act` 세트에 출입국관리법·국적법 근거 항목 2개가 들어갔다.
법령 출처는 다르지만 **고객이 우리를 다시 찾는 지점**이라 같은 흐름에 두는 편이
실무에 맞다고 봤다. 나중에 세트를 법령별로 쪼갤 일이 생기면 이 둘을 먼저 옮긴다.

### 백필이 필요 없었던 이유

의무 템플릿은 고객 생성 시점(`onClientCreated`)에 타임라인으로 복사된다. 즉 템플릿을
고쳐도 **기존 고객의 타임라인은 바뀌지 않는다.** 확인해보니 현재 고객이 0명이라
백필이 필요 없었다. 운영 시작 후 템플릿을 고칠 때는 기존 고객에게 항목을 넣어주는
백필 스크립트가 따로 필요하다는 뜻이기도 하다.

## 2026-08-29 · 판례를 화면에 연결하며

### 왜 Firestore 직접 읽기가 아니라 서버 함수인가

이 프로젝트의 다른 공통 데이터(`regulations`, `regulatoryDelta`, `obligationTemplates`)는
`allow read: if isAuthed()` 규칙을 주고 클라이언트가 `onSnapshot`으로 직접 읽는다.
판례도 같은 패턴을 따르는 게 자연스러워 보였지만 그러지 않았다.

이유는 문서 크기다. `precedents`의 `body`는 최대 40,000자, `holding`은 8,000자다.
Firestore 클라이언트 SDK에는 **필드 선택 조회(`select`)가 없어** 문서를 받으면 본문까지
통째로 온다. 목록 20건이면 수백 KB에서 1MB에 이른다. 목록 화면에서 본문은 쓰지 않는데도.

Admin SDK에는 `select()`가 있다. 그래서 서버에서 요약 필드만 골라 내려주고, 본문은
상세를 열 때 단건으로 가져온다. 기존 패턴을 깨는 것이라 이 노트에 이유를 남긴다.

⇒ **다른 공통 데이터를 추가할 때는 기본적으로 rules + 직접 읽기를 쓸 것.** 본문처럼
   큰 필드를 담는 컬렉션일 때만 서버 함수로 우회한다.

### precedents에 보안 규칙을 만들지 않은 이유

클라이언트가 직접 읽지 않으므로 규칙이 필요 없다. 규칙을 열어두면 나중에 누군가
직접 조회를 붙여 위의 크기 문제가 조용히 재발한다. 서버 함수 하나만 창구로 둔다.

### 표현 규칙 — 사례를 결론처럼 보이게 하지 않는다

전역 §21과 로캐디 사고(2026-08-28, 실재가 확인되지 않는 사건번호가 초안에 인용됨)를
같이 적용한다.

- 사건마다 **법제처 원문 링크**를 노출한다. 업체가 실재를 직접 확인할 수 있어야 한다.
- 요건 연결은 낱말 매칭 기반 **자동 분류**다(`requirementConfidence: 'auto'`).
  화면에 그렇게 표시하고, 사람 검수를 거친 것과 구분한다.
- "이런 경우 허가됩니다" 같은 문장을 만들지 않는다. 사건이 어떤 사유로 다투어졌는지까지다.

### 유학 요건 태그는 화면에 내지 않는다

`REQUIREMENT_HINTS`에 `study_*` 키가 남아 있고 태깅도 되어 있지만, 유학 도메인은
2026-08-28 KoAdmit으로 이관했다. weddingCORE 화면에는 F-6·연장 요건만 노출한다.
태그 자체를 지우지 않는 이유는 이미 태깅된 사건이 고아가 되기 때문이다.

### 함수 배포가 "Cannot determine backend specification"으로 실패하면

`firebase deploy --only functions`가 아래 오류로 죽는 경우가 있다.

```
Error: User code failed to load. Cannot determine backend specification. Timeout after 10000.
```

**코드 문제가 아니다.** CLI가 함수 목록을 뽑으려고 코드를 로드하는 데 주는 시간이
10초인데, 이 프로젝트는 함수가 28개라 그 안에 못 끝낸다(로컬 로딩 자체는 0.5초다).

해결 — 탐지 시간을 늘려서 배포한다.

```bash
FUNCTIONS_DISCOVERY_TIMEOUT=120 npx firebase deploy --only functions:이름
```

에러 문구가 "User code failed to load"라 코드를 의심하게 되는데, 먼저
`node -e "import('./lib/index.js')"`로 로컬 로딩을 재보고 정상이면 이 문제다.

### 배포 대상이 두 군데로 나뉘어 있다

- **웹** — Cloudflare Worker `weddingcore` → weddingcore.net / www.weddingcore.net
  (`npm run deploy:cloudflare`. wrangler OAuth는 죽어 있으니 전역 §15-2 토큰을
  `CLOUDFLARE_API_TOKEN`으로 물려야 한다)
- **함수·Firestore·Storage** — Firebase 프로젝트 `sungpan2026`

`firebase.json`에 hosting 설정이 남아 있지만 실서비스 도메인은 Cloudflare가 받는다.
`npm run deploy:all`은 Firebase Hosting으로 올리므로 실제 사이트에는 반영되지 않는다.

## 2026-08-28 · 유학 도메인을 KoAdmit으로 이관하며

### weddingCORE에서 유학 수치를 전부 걷어낸 이유

같은 기준이 두 저장소에 있으면 한쪽만 갱신되고, 낡은 쪽이 언젠가 화면에 나간다.
실제로 2016년 시간제취업 수치(주중 20시간, 현행 25시간)가 남아 있었다.

최신 수치(대학 명단 2026-02-12, 재정 금액 2025-03-14)까지 지운 것은 **중복 자체가
위험원**이기 때문이다. 명단은 매년 2월, 금액은 요령 개정 때 바뀐다.

`visaRequirements.ts`의 유학 요건 **키는 남겼다.** `REQUIREMENT_HINTS`가 판례 574건을
요건에 연결하는 데 쓰이고 있어, 키를 지우면 태깅된 사건이 어느 요건이었는지 알 수 없게 된다.
분류에 필요한 것은 키와 실마리 낱말이지 수치가 아니다.

### 입학 기준과 비자 기준은 다른 숫자다

교육부 「표준업무처리요령」의 영어 **입학** 기준은 TOEFL iBT 59, 법무부 매뉴얼의
**비자·시간제취업** 기준은 iBT 71이다. KoAdmit의 변경대조 문서가 이 둘을 합치라고
적고 있었으나 원문을 다시 읽어 별개임을 확인했다. 자세한 내용은
`koadmit/docs/sources/지침_변경대조.md` §8.
