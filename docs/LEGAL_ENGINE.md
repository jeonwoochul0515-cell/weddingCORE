# 법률 엔진 설계 — 비자 실무 전문성을 갖춘 코어

목표: weddingCORE가 비자 관련 **현행 법률·시행령·시행규칙·판례·법령해석례·재결례**를
실제로 알고, 그 근거 위에서 문서를 만들고 판단하는 엔진이 된다.

## 지금 상태 (문제)

AI가 법령을 **모른 채** 문서를 쓴다. 그래서 프롬프트에 이렇게 막아놨다.

> "확인되지 않은 사실, 판례, 조문, 날짜를 만들지 않는다."

환각은 막았지만 **전문성은 없다.** 지금 나오는 초안은 "구조는 맞지만 근거가 빈" 문서다.
변호사가 조문을 일일이 채워 넣어야 하므로 자동화의 이득이 절반이다.

법령 수집기(`functions/src/regulations/`)는 만들어져 있으나 인증키가 없어 **한 번도 돈 적이 없다.**

## 목표 구조

```
[근거 저장소]  법령·시행령·시행규칙 조문 / 판례 / 해석례 / 재결례
      │  (법제처 Open API + 수동 보강)
      ▼
[근거 검색]    문서 유형·비자 트랙별로 관련 조문을 골라낸다
      ▼
[문서 생성]    AI에게 조문 원문을 함께 준다 → 근거를 인용해 작성
      ▼
[인용 검증]    AI가 든 조문번호가 저장소에 실제로 있는지 대조
      ▼
[변호사 검토]  근거가 붙은 초안을 검토 → 승인
```

핵심은 **"AI에게 법을 외우게 하지 않고, 찾아서 쥐어준다"**는 것이다.
모델이 기억하는 법조문은 낡거나 틀릴 수 있지만, 저장소에서 꺼낸 조문은 출처가 분명하다.

## 수집 대상

### 법령 (target=law)
| 트랙 | 법령 |
|---|---|
| 공통 | 출입국관리법 / 시행령 / 시행규칙, 국적법 |
| 결혼중개 | 결혼중개업의 관리에 관한 법률 / 시행령 / 시행규칙, 다문화가족지원법, 국제사법, 민법(친족편) |
| 유학 | 고등교육법, 학원의 설립·운영 및 과외교습에 관한 법률 |
| 체류연장 | 출입국관리법 시행규칙(체류자격별 첨부서류) |

### 판례 (target=prec)
혼인무효·사기결혼·손해배상·사증발급거부처분취소 등 비자 실무 쟁점별로 수집.

### 법령해석례 (target=expc)
법제처 해석례. 조문 적용이 모호할 때 실무 기준이 된다.

### 재결례 (target=decc 계열)
중앙행정심판위원회 재결례. **사증발급 거부·체류연장 불허에 대한 행정심판 결과**는
"어떤 사유로 거부되고 어떤 논리로 뒤집히는가"를 담고 있어 이 사업에서 가장 값진 자료다.

## 저장 구조 (Firestore)

기존 `regulations/{statuteId}/articles/{articleId}`를 유지하고 옆에 추가한다.

```
regulations/{statuteId}                 법령 메타 (명칭·시행일·소관부처)
  articles/{articleNumber}              조문 (제목·본문·해시·개정일)
precedents/{caseId}                     판례 (사건번호·선고일·요지·전문)
interpretations/{id}                    법령해석례
rulings/{id}                            재결례 (행정심판)
legalIndex/{trackId}                    트랙·문서유형별 근거 매핑
```

`legalIndex`가 핵심이다. "F-6 신청 패키지를 쓸 때 어떤 조문을 봐야 하는가"를
사람이 한 번 정해두면, 그다음부터 AI가 그 조문을 항상 근거로 삼는다.

## 인용 규칙 (환각 차단)

1. AI에게 **조문 원문을 프롬프트로 준다.** 기억에 의존하지 않는다.
2. 답변에 인용한 조문번호를 별도 필드(`citations`)로 받는다.
3. 생성 후 `citations`의 각 항목이 **저장소에 실재하는지 대조**한다.
4. 없는 조문을 인용했으면 그 문장을 `riskFlags`로 올리고 변호사에게 표시한다.
5. 저장소에 근거가 없는 주제는 **"근거 미확보"로 남긴다.** 지어내지 않는다.

## 갱신과 신선도

- 법령은 개정되면 조문 해시가 바뀐다. 기존 `regulatoryDelta` 구조가 이미 이를 감지한다.
- 개정 감지 시 그 조문을 근거로 삼는 문서 유형에 **재검토 표시**를 띄운다.
- 판례·재결례는 신규만 추가한다(소급 변경 없음).

## 제약 — 먼저 풀어야 할 것

**법제처 Open API는 사전 신청과 서버 IP/도메인 등록이 필요하다.**
현재 인증 없이 호출하면 이렇게 거부된다.

> "OPEN API 호출 시 사용자 검증을 위하여 정확한 서버장비의 IP주소 및 도메인주소를 등록해 주세요."

Cloud Functions는 고정 IP가 없어 IP 등록 방식과 맞지 않는다. 두 가지 길이 있다.

| 방법 | 내용 | 비용·난이도 |
|---|---|---|
| **A. 로컬 수집 (권장)** | 개발 PC IP를 등록하고 스크립트로 수집해 Firestore에 올린다. 법령은 자주 바뀌지 않으므로 주기적 실행으로 충분 | 낮음. 지금 바로 가능 |
| B. 고정 IP | VPC 커넥터 + Cloud NAT로 함수에 고정 IP 부여 후 등록 | 월 비용 발생, 설정 복잡 |

A로 시작하고, 자동 갱신이 꼭 필요해지면 B로 옮긴다.

## 단계별 계획

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | 법제처 Open API 신청 + IP 등록 | **사용자 작업 필요** |
| 2 | 수집 대상 목록 확대 (법령·판례·해석례·재결례) | 준비 |
| 3 | 로컬 수집 스크립트 → Firestore 업로드 | 준비 |
| 4 | `legalIndex` 매핑 (문서유형 ↔ 근거 조문) | 변호사 확정 필요 |
| 5 | 문서 생성 시 근거 주입 + `citations` 수집 | 준비 |
| 6 | 인용 검증 (없는 조문 인용 시 경고) | 준비 |
| 7 | 개정 감지 → 영향 문서 재검토 표시 | 기존 구조 활용 |

## 이 설계가 지키는 선

- **법률 판단을 AI가 대신하지 않는다.** 근거를 모아 주고 초안을 만들 뿐, 승인은 변호사가 한다.
- **없는 근거를 만들지 않는다.** 저장소에 없으면 "확인 필요"로 남긴다.
- **출처를 항상 남긴다.** 어떤 조문·판례를 근거로 썼는지 문서에 표시한다.
