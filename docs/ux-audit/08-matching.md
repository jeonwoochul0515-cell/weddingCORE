# 08 · 매칭 — 사장 시점 점검 (2026-09-05)

점검자 시점. 국제결혼중개업 사장. 휴대폰으로 보고, 화면 글자를 그대로 읽는다. 현지 파트너(베트남·캄보디아 등 현지 소개업체)에게서 후보 여성 여러 명의 사진과 정보를 받아 한국인 고객에게 보여 주고, 맞선 날짜를 잡고, 결과를 적어 두는 것이 매칭 업무의 전부다. 이 일이 이 화면에서 되는지를 코드로 끝까지 따라가며 봤다.

용어 뜻풀이(이 문서에서 쓰는 개발 용어).
- 저장 규칙(firestore.rules) — 서버가 "누가 무엇을 읽고 쓸 수 있는가"를 정해 둔 문서. 화면에 버튼이 없어도 규칙상 허용이면 개발자가 붙일 수 있다는 뜻.
- 컴포넌트 — 화면 조각. "정의만 있고 부르는 곳이 없다"는 말은 조각을 만들어 놓고 어느 화면에도 붙이지 않았다는 뜻.
- 앵커(anchor) — 법정 기한을 계산하는 기준일. 예를 들어 '맞선 예정일'을 적으면 "맞선 7일 전까지 신상정보 제공" 같은 기한이 자동으로 계산된다.

## 발견

### 1. 후보(외국인 여성) 명부가 없다 — 매칭 기록에 이름 넉 자만 손으로 적는다
- 심각도: 막힘
- 어디서: 고객 상세 → 매칭 탭 → [매칭 추가] 창의 "외국측 이름" 칸
- 무슨 일이: 현지 파트너에게서 받은 후보의 이름·나이·국적·사진·학력을 넣어 둘 곳이 어디에도 없다. 후보는 매칭 기록을 만들 때 "외국측 이름"이라는 글자 칸 하나로만 존재한다. 같은 후보를 다음 주에 다시 적으면(예. "응우옌 티 란" / "란") 다른 사람 두 명이 된다. 데이터 설계에는 후보 자료(`Partner` 타입, `partners` 저장 위치)가 있고 저장 규칙도 열려 있지만, 그것을 쓰는 화면이 하나도 없다. 후보 프로필을 저장하는 함수(`updatePartnerProfile`)도 만들어만 두고 부르는 곳이 없다. 그래서 매칭 기록에는 상대방 번호가 늘 빈 문자열(`partnerId=""`)로 저장되고, 궁합 점수도 항상 비어서(`null`) 기록 카드의 "MBTI n점 / 사주 n점" 줄과 추가 창의 점수 안내 줄은 어떤 경우에도 뜨지 않는다. 신상정보 교환 화면에 "외국인 측 신규" 버튼이 있지만 그 폼의 항목은 혼인이력·자녀·건강·범죄경력·직업·소득·재산·거주·가족뿐이고 이름·국적·생년월일 칸이 없어 후보 명부 대용이 되지 못한다. (이미 찾은 "궁합 카드가 늘 '(파트너)'로 비어 있음"의 뿌리가 이것이다. 여기서는 후보 자료 자체가 어디에도 없다는 점을 보고한다.)
- 근거: `src/features/matching/CreateMatchDialog.tsx:76-78`(자유 글자 칸), `src/pages/ClientDetailPage.tsx:62-65, 74-79, 223`(상대 프로필 항상 null, partnerId 빈값), `src/features/matching/useClientProfile.ts:16-24`(정의만, 호출처 0 — `grep updatePartner` 결과 이 파일뿐), `src/types/schema.ts:289-303`(Partner 타입), `firestore.rules:163-166`(partners 쓰기 허용), `src/features/matching/useMatches.ts:72, 79-80`(partnerId·점수 저장), `src/features/matching/MatchHistory.tsx:67-72`(절대 안 뜨는 점수 줄), `src/pages/BackgroundInfoPage.tsx:80-86`, `src/features/sideBySide/fields.ts:40-184`(항목 키 목록)
- 고칠 방향: 고객 아래에 "후보" 목록 화면을 만든다(이름·국적·생년월일·사진·현지 파트너 출처·프로필). 매칭 추가 창의 "외국측 이름"은 글자 입력이 아니라 후보 목록에서 고르게 한다.

### 2. 한 고객에게 후보 여러 명을 나란히 놓고 비교할 화면이 없다 — 비교표(매칭 제안서)는 만들어 놓고 붙이지 않았다
- 심각도: 막힘
- 어디서: 고객 상세 → 매칭 탭 "매칭 기록", 매칭 관리 화면
- 무슨 일이: 사장의 실제 일은 "후보 3~5명을 고객에게 한 번에 보여 주고 고르게 하는 것"인데, 화면은 기록 한 건마다 카드 한 장을 위에서 아래로 쌓을 뿐이다. 후보별 나이·학력·종교·궁합을 한 표에 놓고 비교하는 화면이 없다. 코드에는 "weddingCORE 매칭 제안서"라는 인쇄용 비교표(`MatchReport`)가 완성돼 있는데(양측 프로필 나란히, MBTI·사주 궁합, 조건 대조, 담당 매니저, 인쇄 버튼), 어느 화면에서도 이것을 부르지 않는다. 사장은 이 기능이 있는 줄도 모른다.
- 근거: `src/features/matching/MatchHistory.tsx:49-98`(카드 나열만), `src/features/matching/MatchReport.tsx:41-156`(완성된 제안서), `grep MatchReport` 결과 정의 1곳 외 사용처 0, `src/pages/ClientDetailPage.tsx:10-17`(import 목록에 없음)
- 고칠 방향: 후보 명부(1번)가 생기면 고객 상세에 "후보 비교" 표를 두고, 거기서 `MatchReport`를 "제안서 출력"으로 연결한다.

### 3. 결과 버튼을 한 번 누르면 되돌릴 수 없다 — 확인 창도 없고, '보류'도 끝이다
- 심각도: 위험
- 어디서: 매칭 기록 카드 오른쪽 [수락] [한국측 거절] [외국측 거절] [보류] 버튼
- 무슨 일이: 버튼을 누르면 묻지 않고 바로 저장되고, 저장된 뒤에는 결과 배지만 남고 버튼이 사라진다. 휴대폰에서 작은 글씨 버튼 네 개가 붙어 있어 손가락이 옆으로 가기 쉬운데, 잘못 누른 "외국측 거절"을 "수락"으로 고칠 길이 없다. 특히 '보류'는 "아직 결정 안 함"인데 누르는 순간 종착이 되어 나중에 수락으로 바꿀 수 없다. 저장 규칙은 수정을 허용하지만 화면에 고치는 길이 없다.
- 근거: `src/features/matching/MatchHistory.tsx:34-37`(확인 없이 즉시 저장), `:78-94`(result가 있으면 배지만, 버튼 숨김), `src/features/matching/useMatches.ts:87-97`(결과를 쓰는 함수만 있고 되돌리는 함수 없음), `firestore.rules:218-221`(write 허용)
- 고칠 방향: 결과 배지를 누르면 다시 고를 수 있게 하고, '보류'는 결과가 아니라 "미정" 상태로 둔다. 거절·수락은 한 번 더 묻는다.

### 4. 매칭 기록을 고치거나 지울 수 없다 — 날짜·유형·이름을 잘못 적으면 그대로 남는다
- 심각도: 막힘
- 어디서: 매칭 기록 카드
- 무슨 일이: 기록을 만든 뒤 날짜를 잘못 적었거나(맞선이 미뤄짐), 유형을 잘못 골랐거나, 시험 삼아 만든 기록을 지우고 싶어도 방법이 없다. 카드에는 결과 버튼 외에 아무 조작이 없다. 게다가 "한국측 이름" 칸도 자유 글자라 실수로 고치면 기록에 적힌 이름과 실제 고객이 어긋난 채 저장된다(고객 연결 번호는 그대로인데 이름만 바뀜). 코드에 매칭 삭제 함수가 없다(`deleteDoc`은 사무소 자료와 신상정보 제공 기록에만 있다).
- 근거: `src/features/matching/useMatches.ts` 전체(create·결과 갱신 두 함수뿐), `src/features/matching/MatchHistory.tsx:49-98`, `src/features/matching/CreateMatchDialog.tsx:73-75`(한국측 이름 자유 입력), `grep deleteDoc` 결과 `useOffice.ts:220`, `useDelivery.ts:123`뿐
- 고칠 방향: 카드에 [고치기] [지우기]를 둔다. 한국측 이름은 고객 이름을 자동으로 넣고 고치지 못하게 한다.

### 5. '양측 거절'은 고를 수 없다
- 심각도: 답답
- 어디서: 매칭 기록 결과 버튼
- 무슨 일이: 결과 종류에는 '양측 거절'이 있고 배지 색과 글자도 준비돼 있는데, 버튼 목록은 [수락] [한국측 거절] [외국측 거절] [보류] 네 개뿐이라 둘 다 싫다고 한 경우를 적을 수 없다. 한쪽 거절로 적으면 통계가 틀어진다.
- 근거: `src/features/matching/MatchHistory.tsx:22-28`(라벨에 '양측거절' 있음) vs `:84`(버튼 목록에 없음), `src/types/schema.ts:307`
- 고칠 방향: 버튼에 '양측 거절'을 넣거나, 거절 버튼 하나를 누르면 "누가 거절했나"를 고르게 한다.

### 6. 맞선 날짜를 두 군데 따로 적는다 — 매칭에 적은 날짜로는 법정 기한이 움직이지 않는다
- 심각도: 위험
- 어디서: 매칭 탭 [매칭 추가]의 "날짜" ↔ 컴플라이언스 탭의 "맞선 예정일" 기록 칸
- 무슨 일이: 사장은 매칭 탭에서 "맞선 · 9월 20일"이라고 적으면 맞선 일정을 잡은 것으로 안다. 그런데 법정 기한(신상정보 제공은 맞선 7일 전, 그 밖에 3일 전·1일 전 항목 등 9개)은 컴플라이언스 탭 안에서 따로 "맞선 예정일"을 기록해야만 계산된다. 매칭 기록을 만들 때 그 기준일을 건드리지 않는다. 같은 날짜를 두 곳에 적어야 하고, 한 곳만 적으면 기한 경고가 엉뚱하게 나온다(기준일을 안 적으면 임시 계산값이 붙는다).
- 근거: `src/features/matching/useMatches.ts:69-83`(anchors 안 건드림), `src/features/timeline/TimelineView.tsx:24, 184-222`(맞선 예정일을 따로 적는 칸), `functions/src/timeline/index.ts:212-260`(기준일을 받아 기한 재계산), `functions/src/admin/obligationTemplates.ts:292-431`(맞선 기준 -7·-3·-1일 항목 9개), `:322-329`(기준일 전엔 임시값)
- 고칠 방향: 매칭 유형이 '맞선'이고 날짜를 적으면 그 날짜를 맞선 예정일 기준으로 자동 기록할지 묻는다(또는 자동 반영).

### 7. 생년월일을 두 번 묻고, 사주는 두 번째 것만 본다 — 둘이 달라도 아무도 모른다
- 심각도: 위험
- 어디서: 고객 등록 창 "생년월일"(필수) ↔ 매칭 탭 프로필 폼 "생년월일 (양력)"
- 무슨 일이: 고객을 등록할 때 이미 생년월일을 필수로 받는데, 매칭 탭 프로필에서 또 "생년월일 (양력)"을 묻는다. 사주 궁합은 프로필 쪽 날짜만 쓴다. 등록 때 음력으로 적고 프로필에 양력으로 적거나, 한쪽만 적으면 사주 카드가 비거나 다른 사람 사주가 된다. 음력 생일을 적는 칸은 없다(저장값은 늘 비어 있음). 손님 중엔 음력 생일만 아는 분이 많다.
- 근거: `src/features/agency/CreateClientDialog.tsx:75-76`(등록 시 필수), `src/features/matching/ProfileForm.tsx:77-79`(다시 묻기), `:60`(lunarDate 항상 null), `src/pages/ClientDetailPage.tsx:77-79`(사주는 `birthInfo.solarDate`만), `src/types/schema.ts:257`(등록 생년월일 `koreanClient.birthDate`)
- 고칠 방향: 프로필 폼의 생년월일은 등록값을 자동으로 채우고, "음력입니다" 체크 하나만 추가한다.

### 9. MBTI 궁합 카드에는 "재미로 보기" 표시와 면책 문구가 없다 — 점수표는 출처 없는 손 숫자
- 심각도: 위험
- 어디서: 매칭 탭 "MBTI 궁합" 카드, 매칭 제안서의 MBTI 칸

## 확신이 낮은 항목

- **"거절_A" 같은 저장값은 화면에 나오지 않는다.** 화면에는 '한국측 거절'·'외국측 거절'로 번역되어 뜬다(`MatchHistory.tsx:22-28, 80`). 다만 사전에 없는 값이 들어오면 원값이 그대로 노출된다(`:80`의 `?? m.result`). "한국측/외국측"이라는 말이 사장의 말인지는 업계마다 다를 수 있다(추측). "우리 손님 / 현지 후보"가 더 가까울 수 있다.
- **매칭 기록의 날짜가 하루 어긋날 가능성.** 창에서 고른 날짜(`YYYY-MM-DD`)를 `new Date(v.date)`로 바꾸면 세계표준시 자정이 되어 한국 시각으로는 같은 날 09시다. 한국에서 쓰는 한 표시는 같은 날로 보이므로 문제없을 것으로 본다(추측, 실행 확인 안 함). `CreateMatchDialog.tsx:53`, `MatchHistory.tsx:65`.
- **MBTI 점수표의 출처.** 코드에 출처 주석이 없어 손으로 적은 숫자로 판단했다(`mbtiCompat.ts:8-28`). 어딘가 참고한 표가 있었을 수 있다(추측). 출처가 있더라도 화면에 표시되지 않는 점은 그대로다.
- **사주 예시 날짜의 정확성.** 18번의 "1990년 1월 20일 → 화면 금, 전통 토"는 코드의 계산 방식(양력 연도로 천간 인덱스 계산)을 손으로 따라간 값이다. 만세력과 대조해 실증하지는 않았다.
- **후보 명부가 '사무소 → 현지 파트너' 화면과 헷갈릴 수 있다.** 사무소 화면의 "현지 파트너"는 후보 여성이 아니라 현지 소개업체(회사명·국가·담당자·서면계약 여부)다(`useOffice.ts:65-79`). 사장이 메뉴 이름만 보고 "여기에 후보를 넣는 건가" 하고 들어갔다 나올 가능성이 있다(추측).
