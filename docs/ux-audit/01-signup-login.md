# 01 · 가입·로그인·승인 — 사장 시점 점검 (2026-09-05)

점검자 설정. 국제결혼중개업소 사장. 휴대폰으로 처음 weddingCORE에 들어와 계정을 만들고 업체를 등록해 첫 화면까지 가 본다. 개발 용어를 모르고 화면 글자를 그대로 읽는다.

이미 다른 점검에서 찾은 항목(비밀번호 찾기 없음, 비밀번호 확인 칸 없음, 로그인 실패 문구가 영어 오류 코드, 상단바 내부 ID 노출, 영어 소제목·개발 용어 등)은 다시 적지 않았다. 같은 계열이라도 다른 화면·다른 원인이면 적었다.

용어 풀이(본문에서 쓰는 말).
- 권한 꼬리표(클레임). 로그인 계정에 서버가 붙여 주는 "이 사람은 어느 업체의 무슨 역할" 표시. 이 꼬리표가 없으면 업체 화면에 못 들어간다.
- 저장 규칙. 화면이 서버 창고(Firestore·Storage)에 무엇을 쓰고 읽을 수 있는지 정한 문지기 규칙. `firestore.rules`, `storage.rules`.
- 사진 보관함(Storage). 올린 등록증 사진이 저장되는 곳.
- 공시. 성평등가족부가 공개하는 결혼중개업 등록 업체 명단.
- 글자 읽기(OCR). 사진 속 글자를 자동으로 읽어 입력칸을 채우는 기능.

## 발견

### 1. 등록증을 올린 직후 "주소 얻기"가 저장 규칙에 막혀 가입이 끝나지 않을 수 있다
- 심각도: 막힘
- 어디서: 업체 정보 등록 화면 → "등록 요청" 버튼을 누른 직후
- 무슨 일이: 사진은 올라가는데, 바로 다음에 그 사진의 내려받기 주소를 얻는 단계가 있다. 그런데 사진 보관함의 "읽기" 규칙은 업체 권한 꼬리표가 있는 사람만 통과시킨다. 가입 중인 사장은 아직 꼬리표가 없다. 그러면 제출이 여기서 끊기고 화면 맨 아래에 영어 오류("User does not have permission…")가 뜬다. 다시 눌러도 같은 자리에서 또 끊긴다. 2026-09-01에 갇힌 실제 계정은 `users` 문서조차 없었다(조사 스크립트가 "없음 ← 가입이 끝나지 않음"이라 찍는다). 즉 제출이 2단계(사용자 문서 쓰기) 앞에서 죽었다는 정황과 맞는다. 다만 원인이 정확히 이 규칙인지는 추측이다.
- 근거: `src/pages/AgencySignupPage.tsx:168-170`(올리기 → `getDownloadURL`), `storage.rules:7-8`(읽기는 `token.agencyId == aid` 또는 관리자만), `storage.rules:9-12`(쓰기만 uid 접두어로 허용), `functions/newuser.mjs:11-12`(갇힌 계정 조사), 커밋 `79892d3`(로그아웃 링크만 추가했고 제출 실패 원인은 손대지 않음)
- 고칠 방향: 사진 보관함 읽기 규칙에도 쓰기와 같은 "uid 접두어" 조건을 더하거나, 주소를 화면에서 얻지 말고 저장 경로만 기록한 뒤 서버 함수가 주소를 만들게 한다. 그리고 실제 새 계정으로 가입을 한 번 끝까지 눌러 본다. 배포된 규칙이 파일과 같은지도 확인한다.

### 2. 가입 제출이 중간에 끊기면 다시 제출해도 영원히 거부된다
- 심각도: 막힘
- 어디서: 업체 정보 등록 화면, 두 번째 "등록 요청"
- 무슨 일이: 제출은 다섯 단계를 차례로 한다(사진 올리기 → 내 사용자 문서 쓰기 → 업체 문서 쓰기 → 구성원 문서 쓰기 → 서버에 권한 꼬리표 요청). 전화가 끊기든 지하철에서 신호가 끊기든, 2단계 뒤에서 멈추면 사용자 문서만 남는다. 다시 제출하면 2단계가 "새로 쓰기"가 아니라 "고쳐 쓰기"가 되는데, 고쳐 쓰기 규칙은 이름과 마지막 로그인 시각 두 칸만 허용한다. 만든 시각까지 다시 쓰려 하니 "Missing or insufficient permissions."로 거부된다. 이후로는 몇 번을 눌러도 같다. 유일한 탈출구는 주소창에 `/pending-approval`을 직접 쳐서 "바로 시작하기"를 누르는 것인데, 그 화면으로 가는 링크는 어디에도 없고 사장이 알 방법도 없다.
- 근거: `src/pages/AgencySignupPage.tsx:167-235`(다섯 단계 순서), `firestore.rules:55-60`(users 새로 쓰기 조건), `firestore.rules:61-64`(고쳐 쓰기는 `displayName`·`lastLoginAt`만), `src/pages/PendingApprovalPage.tsx:29-52`(복구 버튼), `src/components/auth/ProtectedRoute.tsx:26-33`·`src/pages/LoginPage.tsx:22-23`(승인 대기 화면은 권한 꼬리표에 agencyId가 있어야 보내는데, 꼬리표는 `functions/src/index.ts:53`에서 agencyId와 role을 한꺼번에 붙이므로 그 상태가 생기지 않는다)
- 고칠 방향: 다섯 단계를 서버 함수 하나로 묶어 한 번에 성공하거나 아무것도 안 남게 한다. 그게 어려우면 재제출 때 이미 있는 문서는 건너뛰고, 가입 화면에 "이전에 제출한 내용으로 이어서 활성화" 버튼을 둔다.

### 3. 결혼중개업 등록번호가 없으면 가입 자체가 안 된다
- 심각도: 막힘
- 어디서: 업체 정보 등록 화면, "결혼중개업 등록번호" 칸
- 무슨 일이: 사업자등록은 했지만 구청 결혼중개업 등록이 진행 중인 신규 업체는 번호가 없다. 그런데 이 칸은 필수라 비우면 "필수 입력입니다."로 막히고, 임의 값을 넣어도 서버가 번호 없는 업체를 거절한다. 사진 자동 읽기도 이 번호는 "있는 경우에만" 읽으라고 되어 있는데 사업자등록증에는 이 번호가 없으니 사실상 항상 손으로 쳐야 한다. 칸에 예시 형식도 없어 무엇을 적어야 하는지 모른다. 같은 화면의 "공시에 아직 등록되지 않은 신규 업체입니다 → 수동 입력으로 진행"이라는 안내가 신규 업체도 가입되는 것처럼 읽히지만, 번호가 없으면 결국 못 들어온다.
- 근거: `src/pages/AgencySignupPage.tsx:380-385`(필수·예시 없음), `functions/src/index.ts:46-48`(번호 없으면 거절), `functions/src/agency/registrationOcr.ts:100`("있는 경우에만"), `src/pages/AgencySignupPage.tsx:353`(신규 업체 안내)
- 고칠 방향: 등록번호를 "나중에 입력"으로 두고 가입은 허용하되, 번호가 채워질 때까지 고객 등록 등 특정 기능만 막는다. 칸에는 "예: 서울-강남-2024-3호"처럼 실제 번호 모양을 예시로 보여 준다.

### 4. 직원 계정을 만들 방법이 없다
- 심각도: 막힘 (겸 위험)
- 어디서: 서비스 전체. 업체 정보·설정 어디에도 "직원 초대"가 없다
- 무슨 일이: 사장 혼자 쓰는 구조다. 직원이 자기 이메일로 가입하면 직원이 아니라 또 다른 업체 사장이 되어 빈 작업공간이 생긴다. 저장 규칙은 "내 uid로 만든 업체의 대표"로만 사용자 문서를 만들 수 있게 하고, 권한 꼬리표도 서버가 대표(owner)로만 붙인다. 설계 문서에는 manager·staff·readonly 역할이 있지만 화면도 서버도 쓰지 않는다. 업체 정보 화면의 "결격사유 점검"에 '종사자'가 있는데 이건 이름 명단일 뿐 로그인 계정이 아니다. 결국 사장은 자기 아이디와 비밀번호를 직원에게 그대로 알려 주게 된다. 직원이 나가도 비밀번호를 바꾸는 것 말고는 끊을 방법이 없다.
- 근거: `firestore.rules:55-60`(users는 본인 업체 대표로만 생성), `firestore.rules:91-99`(members 규칙은 있으나 화면 없음), `functions/src/index.ts:53`(role은 owner 고정), `src/types/schema.ts:95`·`:162`(쓰이지 않는 직원 역할), `src/components/layout/Sidebar.tsx:6-16`(구성원 메뉴 없음), `src/features/office/useOffice.ts:115-119`·`src/pages/OfficePage.tsx:103-118`('종사자'는 명단 항목)
- 고칠 방향: 업체 정보 안에 "직원 초대"(이메일 넣으면 초대 링크 발송) 화면과, 초대받은 사람이 로그인하면 그 업체의 staff 꼬리표를 받는 서버 함수를 만든다.

### 5. 로그인 화면이 한동안 하얗게 비어 있고, 신호가 없으면 영원히 비어 있다
- 심각도: 막힘
- 어디서: `/login`으로 들어온 직후, 그리고 업체 화면 새로고침 직후
- 무슨 일이: 로그인 화면은 "인증 준비가 끝나기 전까지 아무것도 그리지 않는다." 인증 준비는 뒤늦게 코드를 내려받은 다음 서버에 최신 꼬리표를 강제로 다시 물어봐야 끝난다. 느린 휴대폰 망에서는 몇 초간 흰 화면만 보인다. 그리고 그 "다시 물어보기"가 실패하면(터널·지하) 준비 완료 신호가 영영 오지 않아 로그인 화면은 계속 흰 화면, 업체 화면은 "불러오는 중…"에서 멈춘다. 새로고침 말고는 방법이 없고, 왜 그런지 아무 말도 없다.
- 근거: `src/pages/LoginPage.tsx:18`(`if (!initialized) return null`), `src/lib/auth.ts:21-33`(`getIdTokenResult(true)`에 실패 처리 없음, 실패하면 `callback`이 불리지 않음), `src/store/authStore.ts:13`(`initialized`는 `setUser`에서만 켜짐), `src/components/auth/ProtectedRoute.tsx:13-18`("불러오는 중…"), `src/App.tsx:17-20`(인증 코드 지연 로드)
- 고칠 방향: 로그인 화면은 준비 전에도 폼을 그리고 버튼만 잠근다. 꼬리표 갱신이 실패하면 캐시된 꼬리표로라도 `setUser`를 부르고 "연결이 불안정합니다" 한 줄을 띄운다.

### 6. 홈의 "무료로 시작하기"를 누르면 가입이 아니라 로그인 화면이 나온다

### 7. 같은 업체가 두 번 가입돼도 막지 않는다 — 비밀번호를 잊고 새로 가입하면 빈 작업공간이 생긴다
- 심각도: 위험
- 어디서: 가입 전체
- 무슨 일이: 업체 ID는 로그인 계정 ID에서 만든다. 사업자등록번호나 결혼중개업 등록번호가 이미 등록돼 있는지 아무도 확인하지 않는다. 비밀번호 찾기가 없으니(기존 발견) 사장이 다른 이메일로 다시 가입하면, 같은 상호로 텅 빈 두 번째 업체가 생기고 기존 고객·서류는 옛 계정에 남아 못 본다. 사장은 "데이터가 다 날아갔다"고 느낀다.
- 근거: `src/pages/AgencySignupPage.tsx:165`(`ag_` + uid), `functions/src/index.ts:31-65`(중복 검사 없음), `firestore.rules:72-80`(중복 검사 없음)
- 고칠 방향: 서버 함수에서 사업자등록번호·등록번호 중복을 검사하고, 겹치면 "이미 등록된 업체입니다. 그 계정으로 로그인하거나 사무실에 연락해 주세요"와 연락 링크를 보여 준다.

### 8. 관리자의 승인·반려가 사장 화면에 전혀 나타나지 않는다
- 심각도: 답답 (겸 말)
- 어디서: 가입 이후 모든 화면

- 근거: `src/pages/AgencySignupPage.tsx:288-297`(`capture="environment"`로 카메라 직행), `:298-306`("파일 선택 (PDF 가능)"), `:150`(파일 검사)·`:409`(오류 표시 위치)
- 고칠 방향: 버튼을 "사진 찍기 / 앨범·파일에서 고르기"로 바꾸고, 파일이 없으면 1단계 상자를 빨갛게 테두리 치고 그 자리로 화면을 올린다.

### 20. 가입 때 인증 메일이 없어 이메일 오타를 잡을 기회가 없다
- 심각도: 답답
- 어디서: 로그인 화면, 가입 모드
- 무슨 일이: 이메일을 잘못 치고 가입해도 그대로 계정이 생기고 바로 다음 화면으로 넘어간다. 나중에 다른 휴대폰에서 로그인하려 하면 "그런 계정 없음"이 되고, 오타가 무엇이었는지 알 길이 없다. 비밀번호 찾기가 없다는 기존 발견과 겹쳐 계정을 통째로 잃는다.
- 근거: `src/lib/auth.ts:39-41`(계정 생성만), `sendEmailVerification` 호출 없음(`src` 전체 검색)
- 고칠 방향: 가입 직후 확인 메일을 보내고, 등록 화면 상단에 "가입 이메일: ○○○ (맞나요?)"를 한 번 보여 준다. 전화번호를 가입 때 함께 받아 두면 이메일을 잃어도 찾을 수 있다.

### 21. 대표번호(1588·1660으로 시작)는 연락처로 넣을 수 없다
- 심각도: 말
- 어디서: 업체 정보 등록 화면, 연락처 칸
- 무슨 일이: 연락처 규칙이 0으로 시작하는 번호만 받는다. 업체 대표번호 1588-1234를 넣으면 "전화번호 형식이 올바르지 않습니다."가 뜨는데, 사장 눈에는 멀쩡한 번호라 무엇이 틀렸는지 모른다. 사진 읽기도 이 번호는 자릿수가 짧아 버린다.
- 근거: `src/pages/AgencySignupPage.tsx:396`(`^0\d{1,2}-…`), `functions/src/agency/registrationOcr.ts:54-56`(9자리 미만은 버림)
- 고칠 방향: 오류 문구를 "휴대폰 번호(010-…)를 적어 주세요. 기한 알림 문자가 이 번호로 갑니다"로 바꾸거나, 대표번호도 받되 문자 수신용 휴대폰을 따로 받는다.

## 확신이 낮은 항목

- 배포된 저장 규칙이 파일과 같은가. 1번은 `storage.rules` 파일을 근거로 했다. `firebase.json`이 이 파일을 배포 대상으로 지정하지만(`firebase.json` storage 항목) 실제 서버에 올라간 규칙은 이 점검에서 볼 수 없다. 새 계정으로 한 번 끝까지 가입해 보는 것이 가장 빠른 확인이다.
- 아이폰 사진(HEIC)은 자동 인식이 실패할 수 있다(추측). 화면은 `image/`로 시작하는 파일이면 모두 브라우저에서 축소 처리하는데(`src/pages/AgencySignupPage.tsx:38-39`·`:131`), 일부 브라우저는 HEIC를 그리지 못해 "자동 인식에 실패했습니다"로 떨어진다. iOS Safari가 업로드 때 JPEG로 바꿔 주는 경우가 많아 실제 빈도는 확인이 필요하다.
- 카카오톡·네이버 앱 안 브라우저에서 "Google 계정으로 계속하기"가 실패할 수 있다(추측). 구글 로그인은 팝업 방식만 쓰고(`src/lib/auth.ts:43`) 다시 돌아오는 방식(redirect)이 없다(`src` 전체 검색). 앱 내장 브라우저는 팝업을 막는 경우가 많다. 홈 링크가 카톡으로 공유되는 상황을 생각하면 확인해 볼 만하다.
- 비밀번호로 가입한 사장이 같은 이메일의 구글 계정으로 로그인하면 이후 비밀번호 로그인이 안 될 수 있다(추측). Firebase 기본 설정에서 구글은 "신뢰된 제공자"라 인증 안 된 비밀번호 계정을 덮어쓰는 동작이 있다. 코드는 두 방식을 그냥 나란히 제공한다(`src/lib/auth.ts:36-44`).
- 챗봇 말풍선이 휴대폰 로그인·가입 버튼을 가릴 수 있다(추측). 로그인 화면에서 3.5초 뒤 화면 오른쪽 아래에 말풍선(최대 19rem)이 뜨고(`src/components/chat/HaramChat.tsx:44-45`·`:90-118`·`:246`), 가입 화면에도 아바타 버튼이 오른쪽 아래에 고정된다(`src/App.tsx:30`, `HaramChat.tsx:433`). 좁은 화면에서 "가입하기" 링크나 "등록 요청" 버튼 오른쪽 끝과 겹칠 가능성이 있다. 실제 화면으로 확인해야 한다.
